// 01 · CONTEXT & PROBLEM

The Problem: A Developer's Context Is Scattered Across Five Tools

In modern software engineering, developers are bombarded by fragmentation: switching between terminal shells, Slack or Discord communication channels, Obsidian documentation vaults, and cloud LLM web interfaces.

Rather than another generic chatbot, I built Manas: Ciel as one voice for all of it. Ciel works in two modes: answer general technical questions (algorithms, architecture, systems design), or act on my workstation: hand tasks to the five LSFM agents, check hardware vitals, and read the learned rules in my Obsidian notes.

Design Stance: Ciel speaks as a calm, precise peer, not a servant: the system prompt rules out anime-style address such as "Master" or "マスター".

// 02 · DESIGN DECISIONS

Design Decisions & Their Costs

Each card is one decision: what I chose, what I passed over, why, and what it costs. The evidence links point at the public code or result file at a pinned commit.

ADR-CIEL-01

Plain HTTP for Groq, Whisper and Ollama; an SDK only for Gemini

Decision
Groq chat (including streaming), Groq and OpenAI Whisper, and local Ollama are called with Python's urllib. Gemini goes through Google's google-genai SDK.
Alternatives
The groq and openai Python SDKs for every provider.
Why
Groq and Whisper take simple JSON (or a multipart upload) over HTTPS, and Ollama takes the same JSON over plain HTTP on the local machine (127.0.0.1), so the same lightweight standard-library approach covers all three without an SDK, and the retry rules live in my code: Groq's fractional Retry-After (e.g. 1.5 s) is honoured once if it is 4 s or less, then the next model is tried.
Cost
Streaming, multipart uploads and 429 handling are hand-written, so each needs its own tests (GroqRetryAfterTest).
Evidence
llm_client.py · voice_engine.py
ADR-CIEL-02

Speak each sentence as soon as it is written

Decision
Stream the synthesis reply and send each finished sentence to Edge-TTS (up to three requests at once); the HUD plays the clips in order.
Alternatives
Voice the whole reply after the LLM finishes (the 2026-10-01 design).
Why
Time to first audio fell from 4.60 s to 1.41 s p50 (N=10 each, 2026-10-02, same prompt and machine).
Cost
Mission-complete p95 rose from 5.99 s to 7.20 s: the joined replay MP3 waits for the slowest clip, and clips play strictly in order, so one slow clip holds back the sentences after it.
Evidence
before · after · speech_stream.py · ciel_orchestrator.py (clip queue, three at once, in order)
ADR-CIEL-03

Push telemetry over the WebSocket instead of polling

Decision
The server pushes CPU, RAM and disk readings to connected HUDs every 5 s, and samples only while a client is connected.
Alternatives
The HUD polling an HTTP endpoint on a timer (how it worked before).
Why
Nothing is sampled or requested when no HUD is open, and the readings arrive on the WebSocket the HUD already holds for mission events.
Cost
The HUD needs reconnect logic with backoff, and still fetches one snapshot over HTTP when it (re)connects.
Evidence
ciel_server.py (5 s push, snapshot endpoint) · the HUD's reconnect and snapshot code is in hud.js, in a private repo
// 03 · RETROSPECTIVE

What Broke & What I Would Change

⚠️ What Broke in V1

Synchronous weather queries to wttr.in and live web search during voice generation caused the audio stream to block and stutter when the user had high internet latency.

→ The Fix (Shipped)

Fixed, and the code is public in lsfm-ai-hq: every blocking call in a mission now runs in a worker thread via asyncio.to_thread: named mission tools (weather, web search, both LLM calls, psutil, Obsidian, git, Gmail, the PDF build) have per-call timeouts, while FFmpeg runs off the event loop without a timeout. The server's event loop keeps serving other clients while a mission waits. Independent agents run concurrently with asyncio.gather. A call that times out ends as an honest failed ("timed out after N s"), never an empty success. At most two missions run at once; a few more queue, and anything beyond that is refused with a 503 instead of flooding the thread pool. Regression tests prove the loop keeps ticking while a tool blocks.

🛠️ Production Architecture Note

While edge-tts needs no API key and returned an English clip in 0.42 s p50 in the 2026-10-01 bench (a network round trip to Microsoft's service), enterprise production deployment would swap it for self-hosted Kokoro/Vits pipelines or dedicated WebRTC audio streaming to satisfy enterprise uptime SLAs.

// 06 · SIGNAL PROCESSING & DSP

How the Voice Sounds: Audio Cleanup & Voice Filter

Plain text-to-speech sounds flat. To give Ciel a calm, close presence, the pipeline has two FFmpeg stages, one on the way in and one on the way out:

Inbound (speech-to-text prep), piped in memory:
ffmpeg -i pipe:0 -ar 16000 -ac 1 -af "volume=1.8,highpass=f=80,lowpass=f=7500" -f wav pipe:1
Outbound (voice filter over the JA + EN Edge-TTS clips):
[0:a]apad=pad_dur=0.35[a0];[a0][1:a]concat=n=2:v=0:a=1,highpass=f=120,equalizer=f=3500:t=q:w=1.2:g=3.0,aecho=0.85:0.8:25|45:0.18|0.09,volume=0.30

Engineering rationale for these parameters:

  • 16kHz Mono Normalization: Whisper models are trained on 16,000 Hz single-channel audio. Converting the browser's WebM/Opus recording through stdin/stdout pipes avoids temp files and container ambiguity, and the 80 Hz–7.5 kHz band-pass trims rumble and hiss before transcription.
  • Bilingual Sequencing: The Japanese line plays first, then a 350 ms pause, then the English line, so the two voices read as one deliberate utterance rather than an overlap.
  • Presence, Not Speed: A 120 Hz high-pass removes room boom and a +3 dB lift at 3.5 kHz adds clarity. The voices themselves are tuned slightly lower and slower (−2 to −3 Hz pitch, −1 to −2% rate) for a calm delivery.
  • "Inside the Mind" Echo: Two faint reflections at 25 ms and 45 ms create the sense of an internal thought rather than an external loudspeaker, without the smear of a full reverb.
  • Bounded Audio Cache: Rendered replies are kept in audio_cache/; on server start-up only the 35 most recent files are kept, so the cache can't grow without bound.

// 08 · BACKGROUND CHECKS

Background Checks: Ciel Speaks Up First

Passive voice assistants only speak when spoken to. Ciel runs a background-check loop (proactive_sentinel.py) every 45 seconds while the HUD is connected, ranks what it finds (warning > action > info), and surfaces the top 3 across 4 checks:

⚡ Hardware Check

Reads psutil vitals and warns when CPU load passes 85%, RAM passes 88%, or drive C: drops under 20 GB free. Each warning offers a one-click hand-off to Eunchae.

🗓️ Daily Log Check

Opens today's Obsidian daily log. If it's missing, Ciel suggests Sakura's briefing; otherwise it routes the first unchecked priority to the matching agent by keyword.

📄 Portfolio Check

Scans the portfolio's index.html for leftover TODO or FIXME markers and offers a Yunjin audit.

🐙 Git Check

Runs git status --porcelain on the workspace and, at 3 or more uncommitted changes, offers a Kazuha review of the diff.

When an anomaly is flagged, Ciel displays an advisory telemetry badge on the Voice HUD (e.g. ✦ 2 ADVISORY) and emits a non-intrusive notification toast allowing one-click resolution.

Streaming Speech: Time to First Audio

The table above shows the cost: no sound until the whole reply had been voiced. Ciel now streams the synthesis reply and voices each spoken sentence as soon as the LLM finishes writing it (up to three Edge-TTS requests at once). The HUD plays the clips in order while the rest is still being generated. Time to first audio runs from the start of the mission until the first playable audio URL is broadcast to the HUD; the HUD's fetch of a local file comes on top.

FULL MISSION, N=10 EACH BEFORE (WHOLE REPLY) AFTER (PER SENTENCE)
Time to first audio, p50 / p95 4.60 s / 5.99 s 1.41 s / 2.00 s
Mission complete, p50 / p95 4.60 s / 5.99 s 4.29 s / 7.20 s

Measured 2026-10-02 with bench/bench_ciel.py --stages e2e_mission --runs 10: the same general-knowledge prompt, Groq paced 45 s between runs, on an Intel Core i5-12400F, Windows 11, Python 3.11.9, ffmpeg 9.0.2, edge-tts 7.2.8. Network round trips from this machine, not compute times; with 10 runs, p95 is the max. Code: LE-SSERAFIM-AI-HQ 3315b69 (before) and 3eedda9 (after), public in lsfm-ai-hq since 14a319f (speech_stream.py). Full results: ttfa-before.md, ttfa-after.md.

The trade-off is in the second row. The first sentence is heard about 3.2 s sooner at p50, but the joined MP3 kept for replay waits for the slowest clip. In one of the ten runs a single Edge-TTS clip took 6.2 s, which set the 7.20 s worst case. Clips play strictly in order, so a slow clip also holds back the sentences after it; the pauses this causes between sentences are not measured yet.
