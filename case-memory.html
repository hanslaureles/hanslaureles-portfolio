Cognitive Memory Core — Zero-Dependency
Self-Improving Agent Flywheel

Tackling the "Session Amnesia" dilemma in AI code assistants. We engineered a zero-dependency cognitive memory flywheel that performs BM25 episodic heuristic recall before code is generated, records post-mortems of user corrections, and auto-crystallizes high-impact heuristics into authoritative workspace guidelines.

Problem
Coding agents forget corrections between sessions and repeat the same mistakes.
Constraint
Recall runs before every task on a local workstation, so it uses the Python standard library only: no model download, no vector database.
Decision
Field-weighted BM25 with tag and severity boosts over a JSONL store of post-mortems.
Measured result
On 30 held-out queries: recall@3 0.90, MRR 0.87, 0.81 ms p50 on the 10-entry store (i5-12400F, Python 3.11, 2026-10-02). A naive substring baseline scores about the same at this size (eval).

// 01 · CONTEXT & MOTIVATION

The Dilemma: AI Session Amnesia

Contemporary AI coding assistants are fundamentally stateless between sessions. Every new conversation, branch switch, or tool invocation begins with a clean slate. This creates a frustrating, repetitive developer experience:

  • Regression Loops: An agent repeats known anti-patterns (e.g. nested PowerShell quotes, robotic copy on lifestyle brands, or Netlify subdirectory 404 order).
  • Tacit Knowledge Loss: Non-obvious nuances uncovered through painful debugging are lost the moment the chat window closes.
  • Context Window Bloat: Shoving entire multi-thousand-line project histories into prompt headers wastes token bandwidth and degrades attention quality.

Instead of treating AI agents as ephemeral chat participants, we treated them as compounding knowledge engines. The goal: an agent that becomes measurably smarter after every user correction.

// 04 · ALGORITHMIC MECHANICS

Mathematical Retrieval Mechanics

Vector embeddings alone frequently struggle with precise syntactic rules (e.g. distinguishing `"` from `'` in PowerShell or exact CSS properties like white-space: nowrap). We designed a domain-weighted BM25 scoring algorithm:

Score(D, Q) = ∑ IDF(qᵢ) · [ (TF_weighted · (k₁ + 1)) / (TF_weighted + k₁ · (1 - b + b · (|D| / avgDL))) ] · SeverityMult · FreqMult

Key architectural nuances:

  • Multi-Field Weighting: Tags are weighted at 3.0×, triggers at 2.5×, and symptoms at 2.0× relative to generic code diffs.
  • Frequency Compounding: Lessons encountered multiple times receive an automatic multiplier (1.0 + min(0.5, (freq - 1) * 0.1)), ensuring battle-tested rules rank highest.
  • Zero Dependencies: No PyTorch, no HuggingFace, no ChromaDB. Pure Python standard library ensures instant execution across any terminal or CI/CD container.

What this shows: on today's 10-entry store, BM25 is not clearly better than a substring search. It ties on MRR, and with 10 entries a top-3 list covers 30% of the store, so recall@3 says little. Its three misses are paraphrases with no shared words, such as "add numbers to the achievements in my CV" for the résumé-metrics rule, which no keyword method can catch. Latency grows linearly with the store, because every call re-reads and re-scores it. CI now fails if BM25 recall@3 or MRR falls below these numbers minus a tolerance.

Architectural Decision: Why BM25 over Dense Vector Embeddings?

Many AI agent memory solutions reach prematurely for heavy vector databases (ChromaDB, Pinecone, FAISS) and deep learning frameworks (PyTorch, transformers). For a local store of a few hundred guidelines, dense embeddings add a model download, an embedding step on every write, and a dependency stack to maintain, and they can blur exact technical identifiers (e.g. sys.stdout vs sys.stdin) that a keyword match keeps apart.

By choosing standard library field-weighted BM25 with tag boosting, retrieval runs in 0.8 ms at p50 (about 1.5 ms worst case across 2,000 calls on the current 10-entry store; measured with bench_recall.py on an Intel Core i5-12400F, Windows 11, Python 3.11, 2026-10-01), holds nothing in memory between calls, and matches exact error codes like TerminatorExpectedAtEndOfString as single tokens. The trade-off is in the eval above: it misses paraphrases that share no words with the rule, and past a few hundred entries it would need a precomputed index.

Retrospective: What Broke & What I Would Change

⚠️ What Broke in V1

Unmeasured retrospective, recalled rather than logged: naive substring matching seemed to fire on generic coding words like error, file, and test, injecting unrelated rules into the prompt context. The held-out eval above measures recall, not false positives, so it neither confirms nor rules this out.

✓ The Engineering Fix

Implemented tokenization with an English coding stopword filter, added 3.0× weighting to exact domain tags, and introduced severity multipliers (1.4× for critical bugs) to isolate true matches.
