Case Study 01 · Multi-Agent System Applied AI Systems Multi-Agent Orchestration

LSFM AI HQ — Five AI Agents
for My Inbox, Job Search & Code

Five Discord agents, each with one job. Each agent calls its own Groq or Gemini model and falls back to the other provider, or uses a local Ollama model on an AMD RX 6600 XT. They sort Gmail into labels and build one-page ATS resumes with headless Edge or Chrome. Job applications wait in an approval channel, and mail is never deleted.

● The Engineering Challenge

Hosted multi-agent setups bill for every model call, so cost grows with each agent and task; they also create brittle single-point-of-failure network dependencies, and hide agent decision states inside terminal black boxes where users cannot intervene.

● The Architecture Solution

Engineered an asynchronous 5-agent system on Discord Gateway with operator-selectable routing: per-agent cloud models on Groq and Gemini, each with the other provider as a cross-provider fallback, and a local Ollama mode (qwen2.5-coder:7b on an RX 6600 XT) for private work, switchable live with !mode.

// 01 · CONTEXT & MOTIVATION

Too Many Tabs, Too Much Busywork

A lot of my day went to busywork spread across separate tools: digging through promotional email to find the university or banking messages that mattered, reformatting resumes for each applicant tracking system (ATS), and switching between browser tabs.

While commercial AI assistants exist, they suffer from two fundamental design flaws:

1. High Recurring Subscription Overhead

Cloud-only multi-agent platforms incur unpredictable API token bills and subscription fatigue that scale rapidly without guarantee of uptime or privacy.

2. Monolithic Chatbot Bottleneck

A single chat window forced to handle calendar, email, resume formatting, and job tracking collapses under context pollution and loses specialization.

“How might we architect a self-hosted operations headquarters where specialized AI agents coordinate autonomously over familiar interfaces, backed by local GPU acceleration?”

LSFM AI HQ was engineered from first principles to solve this: a distributed, multi-agent platform running on personal hardware, orchestrating dedicated domain specialists through a unified Discord interface with real-world tool execution.

// 02 · DESIGN DECISIONS

Design Decisions & Their Costs

Each card is one decision: what I chose, what I passed over, why, and what it costs. The evidence links point at the public code or result file at a pinned commit.

ADR-LSFM-01

Rules first, the LLM only for unknown mail

Decision
Sakura's Gmail classifier checks sender, domain and keyword rules first. Only mail no rule recognises goes to the LLM (temperature 0.1). The prompt asks for JSON only; the classifier pulls a JSON object out of the reply when there is one, and falls back to a rule-based label when there isn't.
Alternatives
Send every email to the LLM.
Why
Common senders (job platforms, banks, shops, newsletters) get the same label every time with no model call; the LLM only handles the long tail.
Cost
The rule lists are maintained by hand, and neither tier's accuracy is measured yet: there is no labelled email set.
Evidence
gmail_engine.py
ADR-LSFM-02

A separate two-thread pool for heavy jobs

Decision
PDF builds (headless Edge, up to 25 s), Gmail triage and sweeps run on their own 2-worker pool. LLM text calls stay on asyncio's default executor.
Alternatives
Run everything on the default executor.
Why
A burst of heavy jobs could take every default thread and make quick calls (vitals, chat replies, Obsidian reads) wait behind them.
Cost
Only two heavy jobs run at once; the rest queue. LLM calls deliberately stay off this pool, or a chat reply would wait behind a PDF build.
Evidence
heavy_jobs.py
// 03 · RETROSPECTIVE

What Broke & What I Would Change

⚠️ What Broke in V1

Unbounded asynchronous Discord Gateway event listeners without rate-limit backoff triggered HTTP 429 rate limit exceptions from Groq API during sudden batch notification spikes.

✓ The Engineering Fix

Added a second provider: any Groq failure, including a 429, now falls through to Gemini instead of failing the request. What I'd change next: there's still no retry with backoff and no shared rate limiter across the five agents, and the HTTP calls are blocking (run in worker threads). V2 moves to an async client with a token bucket and jittered exponential backoff.

// 05 · INFERENCE RUNTIME

Multi-Provider Routing: Groq, Gemini & an Optional Local GPU

A core engineering priority was high-quality output within provider rate limits without locking the system to one provider. Every agent calls a single dispatcher, query_llm(), whose behavior the operator switches live from Discord with !mode local | cloud | auto:

  • Cloud mode (per-agent model, cross-provider fallback): Each agent has its own cloud model (table below). Sakura, Chaewon, Kazuha and Eunchae go to Groq first; if Groq errors or is rate-limited, the same prompt is retried on Google Gemini (gemini-3.6-flash). Yunjin runs the other way round: Gemini first, then Groq (qwen/qwen3.8-27b) before the call fails.
  • Local mode (Ollama): Runs qwen2.5-coder:7b on the workstation's AMD Radeon RX 6600 XT, keeping prompts on the machine. Local mode fails fast if Ollama isn't running rather than silently sending prompts to the cloud.
  • Auto mode (local first): Probes Ollama with a 1.2 s health check; if it's up, the local model answers, and any local error falls through to the cloud chain above.
  • What it does not do (yet): There is no automatic cloud-to-local failover. When both cloud providers are exhausted in cloud mode, the request fails with the collected provider errors.
Engine / Model Assigned To Provider Why We Use It
qwen/qwen3.8-27b Sakura, Kazuha · default cloud model · Yunjin's fallback Groq Orchestration and code work on Groq's low-latency LPUs.
openai/gpt-oss-120b Chaewon Groq The larger model for resume and cover-letter writing.
openai/gpt-oss-20b Eunchae Groq A small, fast model for frequent QA and health reports.
gemini-3.6-flash Yunjin · cloud fallback for the other four Google Yunjin's design critiques, and a second provider so a Groq outage or rate limit doesn't fail the request.
gemini-embedding-001 Kazuha's RAG index Google 3072-dimension embeddings for the SQLite knowledge-base vector store.
qwen2.5-coder:7b All agents in local / auto mode Ollama · RX 6600 XT Keeps prompts on the workstation when privacy matters more than output quality.

Model names come from DEFAULT_CONFIG in llm_client.py, and the mode and models can be overridden in memory/brain_mode.json.

Show the query_llm() code
llm_client.py // query_llm() (condensed)
def query_llm(prompt: str, system_instruction: str = "", temperature: float = 0.4) -> str:
    mode = get_brain_mode()                # "local" | "cloud" | "auto", set via !mode
    errors = []

    if mode == "local":
        if not check_ollama_status()[0]:
            raise RuntimeError("Brain mode is 'local', but Ollama is not running")
        return call_local_ollama(prompt, system_instruction)   # qwen2.5-coder:7b

    if mode == "auto":
        ollama_up, models = check_ollama_status()          # 1.2 s probe of :11434
        if ollama_up and models:
            try:
                return call_local_ollama(prompt, system_instruction)
            except Exception as e:
                errors.append(f"Local Ollama: {e}")        # fall through to cloud

    # Cloud chain: Groq first, Gemini as the cross-provider fallback
    # (agents whose model is Gemini, i.e. Yunjin, run the reverse: Gemini, then Groq)
    try:
        return call_groq(prompt, system_instruction, temperature=temperature)
    except Exception as e:
        errors.append(f"Groq Cloud: {e}")
    try:
        return call_gemini(prompt, system_instruction, temperature=temperature)
    except Exception as e:
        errors.append(f"Gemini: {e}")
    raise RuntimeError(f"All LLM providers failed: {'; '.join(errors)}")
// 06 · REAL-WORLD APIS & TOOLS

Deterministic Automation: Headless PDF & Gmail Triage

Language models are only as useful as their ability to alter state in the real world. LSFM AI HQ integrates two critical programmatic tools:

Headless ATS Resume Compilation Engine
Single-Page Strict Formatting via Microsoft Edge
PDF_ENGINE
  • Parses structured markdown specifications into calibrated HTML/CSS with exact point-based typography and line heights.
  • Launches Microsoft Edge in headless mode (--headless --disable-gpu --print-to-pdf) to compile a pixel-perfect, 1-page PDF directly to vector format.
  • Renders the resume as real, selectable PDF text rather than an image, so no OCR is needed and it stays parseable by automated Applicant Tracking Systems.
Google Workspace OAuth2 Batch Triage Engine
Sorts Mail into 10 Labels; Archives, Never Deletes
GMAIL_ENGINE
  • Integrates with Google Gmail API using OAuth2 user credential refreshes with secure local token storage.
  • Provisions 10 nested labels (LSFM/Interviews, LSFM/University, LSFM/Finance, LSFM/Clutter) and classifies unread emails using structured JSON prompts.
  • Features an automated !clean sweep that safely archives non-urgent newsletters while keeping critical university, human VIP, and banking notices highlighted.

Safety Rules the Agents Can’t Break

RELIABLE AUTOMATION · HUMAN IN THE LOOP

Autonomous agents are only helpful if you can trust them. LSFM HQ enforces three boundaries:

🛡️
No Delete Path

The Gmail engine can only add labels and archive; there is no Gmail trash or delete call anywhere in the codebase. Bulk sweeps (!clean, !cleanse) run only when the operator types the command.

🔒
Credentials Stay Local

API keys and OAuth tokens live in git-ignored local files. Cloud mode sends prompts to Groq and Google; switching to local mode keeps inference on the workstation's GPU.

🔄
Independent Reconnects

run_all.py starts each bot as its own asyncio task with a reconnect loop and backoff, so one bot's gateway error never takes the other four down.

Email Triage: How Classification Works

Sakura's Gmail engine performs automated classification across 10 custom Gmail labels with non-destructive bulk-archiving. Each unread message passes through two tiers:

  • Tier 1 · Deterministic rules: known senders, domains, and keywords map straight to a label with no model call, so common mail is fast and fully predictable.
  • Tier 2 · LLM classifier: anything the rules don't recognize is classified by the LLM into a strict JSON category, parsed defensively, and mapped to one of the LSFM/ labels.
  • Bulk sweeps: !clean and !cleanse archive promotions and newsletters by changing labels only. Nothing is trashed or deleted, so every sweep can be undone from All Mail.

🛠️ Engineering Transparency: How I Built This

This system was designed and developed through an iterative AI-assisted engineering workflow. I authored how the 5 agents split the work, designed the structured JSON output contracts, wrote the test suite, and verified every generated prompt and system invariant, while leveraging AI agent pairing (Google Antigravity) for rapid boilerplate scaffolding, API client generation, and documentation review.
